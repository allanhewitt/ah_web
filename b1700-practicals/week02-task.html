Importing Data and Establishing Trust

Group Task Sheet · Core → Transfer → Extension

Why this matters

Central question: Did the data enter R correctly, and should we trust what came in?

A file can import without an error and still be unfit for analysis. Every downstream result depends on the integrity of the data foundation.

How to work this week

Work through this page in order as a small group. This task page is your activity script.

Use the supplied Week 2 RStudio project as your shared workspace. It contains the datasets, setup code and labelled spaces for each phase. Decide together what analysis or code is needed, and keep brief notes or comments in week02_session.R as you work. The R file is not a completed solution.

If your group gets stuck, open the Week 2 Hint Sheet and use the hint for the relevant task. Use as little support as you need, then return to the task.

Use one active RStudio project per group and rotate the person operating RStudio during the activity. Everyone should be able to explain the group's decisions.

PHASE 1 — RETRIEVAL

Reconnect Week 1 ideas with the problem of trusting imported data.

Task 1.1 — Test three claims

As a group: Decide whether you agree with each statement and explain why:

  • If a column is numeric in R, it should be treated as a quantity.
  • If read_csv() returns no error, the imported data are ready for analysis.
  • Repeated player IDs can be legitimate when one row represents a player appearance rather than one player.
Record: Write a brief agree/disagree justification for each claim in the Phase 1 section of the R script.

PHASE 2 — CONSEQUENCE PROBLEM

Apply the trust principle before any analysis begins.

Task 2.1 — Decide what must happen first

A GPS export imports successfully. One important variable has an awkward representation, some values are missing, and one identifier does not match the roster. A coach needs a report this afternoon.

As a group: Decide what should happen before any performance analysis begins.

Record: Write a short response that identifies the checks you regard as essential and why.

PHASE 3 — CORE PRACTICAL

Establish what can reasonably be trusted before analysis.

Task 3.1 — Establish the grain of each table

The Week 2 project contains players, matches and tracking, loaded from the three supplied CSV files.

As a group: Inspect all three tables and state what one row represents in each.

Record: Write one clear grain statement for each table.

Task 3.2 — Check that the objects are what you expected

As a group: Record the number of rows, number of columns and variable names for each table. Decide whether the dimensions and fields match the objects you expected to import.

Record: Keep a concise structure check for all three tables.

Task 3.3 — Check representations that matter

As a group: Check the classes of the most important identifiers, squad_number, contract_end and selected numerical performance variables such as distance_km and match_rating. Focus on representations that could affect later analysis.

Record: Note only the representations that are analytically important or potentially problematic.

Task 3.4 — Convert and verify the contract dates

As a group: Convert contract_end from day/month/year into an R date. Then verify the result: check the class, whether unexpected missing values were created, some converted values, and the minimum/maximum date. Decide whether the years and date range look plausible.

Record: Record your verification evidence, not just that the conversion ran.

Task 3.5 — Check missingness and plausibility

As a group: Check missingness in important tracking variables and inspect plausible ranges for selected numerical fields. Identify anything that deserves investigation.

Record: List the concerns you found and distinguish “missing” from “present but potentially implausible”.

Task 3.6 — Check identifier coverage

As a group: Test whether every player_id in tracking exists in the player table and every match_id exists in the match table.

Record: Record whether each coverage check passed. If not, identify the unmatched values before judging them.

Task 3.7 — Write a trust statement

As a group: Summarise the status of the Strathclyde FC data in two parts: what you have verified and what remains uncertain.

Record: Write the two-part trust statement in the R script.

PHASE 4 — CHECKPOINT

Make the trust workflow explicit before moving to a fresh dataset.

Task 4.1 — Checkpoint the trust workflow

IMPORT → INSPECT → CHECK → VERIFY → STATE WHAT REMAINS UNCERTAIN

As a group: Make sure you can explain why a successful import is only the beginning of this process.

Record: Write one sentence identifying the main risk this workflow is designed to prevent.

PHASE 5 — TRANSFER

Apply the trust workflow to an unfamiliar athletics dataset.

Task 5.1 — Diagnose the athletics results before changing them

Open week02_transfer_results.csv.

As a group: For each concern you identify, decide whether it is primarily a representation problem, a possible data-quality problem, a legitimate unusual value, or something that cannot be resolved without the original source. Pay particular attention to dates, a result such as DNS, digit-based codes and numerical performance fields.

Record: Create a concise diagnosis before making any changes.

Task 5.2 — Make only defensible changes

As a group: Decide which issues can be changed on the evidence available and which should be left or flagged for investigation.

Record: Document any change you make and the evidence that justifies it.

PHASE 6 — EXTENSION

Push beyond checking syntax to the limits of what the file itself can establish.

Task 6.1 — Produce a trust audit

As a group: Separate what you can verify from the transfer file itself from what would require checking the original data source. The focus is the quality of the audit, not the number of functions used.

Record: Write a brief trust audit with “Verified from file” and “Requires source check” sections.

PHASE 7 — DEBRIEF

Connect the technical checks with professional analytical responsibility.

Task 7.1 — Explain why inspection is professional practice

As a group: Why is “inspect before analyse” a professional responsibility rather than merely good R practice?

Record: Write one or two sentences that your group could defend to a coach or colleague.
Assessment One connection: import, grain, focused type/date checks, missingness/plausibility and identifier coverage are part of the common core.
