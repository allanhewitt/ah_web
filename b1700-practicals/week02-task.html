Importing Data and Establishing Trust

Group Task Sheet · Core → Transfer → Extension

WHY THIS MATTERS

Central question: Did the data enter R correctly, and should we trust what came in?

A file can import without an error and still be unfit for analysis. Every downstream result depends on the integrity of the data foundation.

How to work this week

In the demonstration you checked the players table. Here you apply the same checks to different tables: matches, then tracking. The techniques are the ones you have already used. What changes is the table, the column names and, often, the answers.

Work through this page in order as a small group, in your own script (your script from the demonstration is a good starting point). Keep brief comments as you go, so that your script records both what you ran and what you concluded. A script of bare commands is not a record of your thinking.

If your group gets stuck, open the Week 2 Hint Sheet and use the hint for the relevant task. Hints show patterns with placeholders, such as class(table$column). You supply the real table and column names. Use as little support as you need, then return to the task.

Use one active RStudio project per group and rotate the person operating RStudio. Everyone should be able to explain the group's decisions.

PHASE 1: SET UP

Start from a clean session and bring in the other two tables.

Task 1.1: Restart and import

Use Session > Restart R so that nothing from the demonstration is left in memory. Check that week_two.Rproj is the open project. Start a new script, save it, and load the tidyverse.

As a group: Import the three tables into objects called players, matches and tracking. The files are in the data folder: players.csv, match_results.csv and player_match_tracking.csv.

Record: Add a comment to your script noting that each import ran without an error. Then note what that does and does not tell you.

Task 1.2: First look at the two new tables

As a group: Take a first look at matches and tracking in the same way as you did for players. Decide what stands out and what you would want to check.

Record: Write two or three comments listing what you would check, before you start checking.

PHASE 2: CORE: THE MATCHES TABLE

Repeat the players checks on a table with different grain and a different date column.

Task 2.1: Grain of matches

As a group: State what one row represents. Then decide what a repeated match_id in this table would tell you, and how that differs from a repeated player_id in tracking.

Record: One grain statement and one sentence on repeated IDs.

Task 2.2: Dimensions and names

As a group: Record the number of rows, the number of columns and the variable names. Decide whether this is the object you expected to import.

Record: A concise structure check for matches.

Task 2.3: Representations that matter

As a group: Check the classes of match_id, date, goals_for and goals_against. Decide which, if any, would obstruct later analysis.

Record: Note only the representations that are analytically important or potentially problematic.

Task 2.4: Convert and verify the match dates

As a group: The dates are stored as day/month/year. Convert them into R dates, then verify the result: class, unexpected missing values, some converted values, and the earliest and latest date. Decide whether you will overwrite date or create a new variable, and give a reason. Finally, decide whether the date range looks like a single football season.

Record: Your verification evidence and the reasoning behind your naming choice. Not just that the conversion ran.

Task 2.5: Missingness and plausibility in matches

As a group: Check for missing values in the important variables, including the converted dates. Then use the smallest and largest values to ask whether goals_for and goals_against are plausible.

Record: Your findings, distinguishing “missing” from “present but potentially implausible”.

PHASE 3: CORE: THE TRACKING TABLE

Now a larger table with a different grain, where the checks connect to the matches table.

Task 3.1: Grain of tracking

As a group: State what one row represents. Decide what repeated player_id and repeated match_id values mean in this table.

Record: One clear grain statement.

Task 3.2: Dimensions, names and expectations

As a group: Record the rows, columns and variable names. Then compare nrow(tracking) with nrow(matches). What relationship do you find, and what would it imply about how many players are tracked in each match?

Record: The structure check, plus the relationship you found and what you infer from it.

Task 3.3: Representations that matter

As a group: Check the classes of match_id, player_id, minutes_played, distance_km, sprints and match_rating. Decide which are identifiers and which are quantities, and whether R has represented each one as you would expect.

Record: Note only what is analytically important or potentially problematic.

Task 3.4: Missingness in tracking

As a group: Count the missing values in each of the numerical variables. Identify which variables have missing values and how many.

Record: A short list of what is missing and where.

Task 3.5: Plausibility in tracking

As a group: Find the smallest and largest value of minutes_played, distance_km, sprints and match_rating. If any summary does not return a number, work out why before moving on. Use your football knowledge to judge whether each range is plausible, and identify anything that deserves investigation.

Record: Each range, your judgement of it, and any concern. Keep “missing” separate from “present but potentially implausible”.

PHASE 4: IDENTIFIERS AND TRUST

Test whether the tables can be linked, then state what you can and cannot claim.

Task 4.1: Identifier coverage

As a group: Adapt the coverage check to test whether every player_id in tracking exists in players, and whether every match_id in tracking exists in matches.

Record: Whether each check passed. If one fails, identify the unmatched values before judging them.

Task 4.2: Does the direction matter?

As a group: Now reverse each check: does every player in players appear in tracking, and does every match in matches appear in tracking? Decide what a FALSE would mean in each direction, and whether the direction you test matters.

Record: The results and one sentence on why direction matters (or does not).

Task 4.3: Write a trust statement

As a group: Summarise the status of the matches and tracking tables in two parts: what you have verified and what remains uncertain. Then write one sentence on the main risk this workflow is designed to prevent:

IMPORT → INSPECT → CHECK → VERIFY → STATE WHAT REMAINS UNCERTAIN

Record: The two-part trust statement and the one-sentence risk, as comments in your script.

PHASE 5: TRANSFER

Apply the trust workflow to an unfamiliar athletics dataset.

Task 5.1: Diagnose the athletics results before changing them

Open week02_transfer_results.csv.

As a group: For each concern you identify, decide whether it is primarily a representation problem, a possible data-quality problem, a legitimate unusual value, or something that cannot be resolved without the original source. Pay particular attention to dates, a result such as DNS, digit-based codes and numerical performance fields.

Record: A concise diagnosis before making any changes.

Task 5.2: Make only defensible changes

As a group: Decide which issues can be changed on the evidence available and which should be left or flagged for investigation.

Record: Any change you make and the evidence that justifies it.

PHASE 6: EXTENSION

Push beyond the checks you have been shown.

Task 6.1: Check the structure you expected

As a group: From Task 3.2 you expect 14 tracking rows per match. Devise a check that tests whether this holds for every match. Then devise a check on how many players in each position appear in each match, and ask whether the result is what a football match would produce.

Record: What you checked, what you found, and whether it is a problem, a legitimate unusual value, or something you cannot resolve from the file.

Task 6.2: Produce a trust audit

As a group: Separate what you can verify from the files themselves from what would require checking the original data source. The focus is the quality of the audit, not the number of functions used.

Record: A brief trust audit with “Verified from file” and “Requires source check” sections.

PHASE 7: DEBRIEF

Connect the technical checks with professional analytical responsibility.

Task 7.1: Explain why inspection is professional practice

As a group: Answer: Why is “inspect before analyse” a professional responsibility rather than merely good R practice?

Record: One or two sentences that your group could defend to a coach or colleague.

Assessment One connection: import, grain, focused type/date checks, missingness/plausibility and identifier coverage are part of the common core.
