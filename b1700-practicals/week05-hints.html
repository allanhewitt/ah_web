PHASE 1 — RETRIEVAL

Hint for Task 1.1 — Recall grain and preservation

players has one row per player; tracking has one row per player appearance. A player ID can therefore repeat legitimately in tracking.

PHASE 2 — CONSEQUENCE PROBLEM

Hint for Task 2.1 — Interpret an unexpected row loss

Ask which table was meant to define the observations, what join type was used, and whether unmatched records were supposed to survive.

PHASE 3 — CORE PRACTICAL

Predict first; verify after.

Hint for Task 3.1 — Predict the small join

Look for a field that should represent the same identity in both tables. State the events-table grain before inspecting matches.

Hint for Task 3.2 — Use a left join with an explicit expectation
joined <- events |>
  left_join(player_info, by = "player_id")

A left join preserves every row on the left and adds matching information where available.

Still stuck?

Before running the join, write down nrow(events). After the join, compare the row count. If the left-side grain is meant to be preserved, that expectation should guide your interpretation.

Hint for Task 3.3 — Diagnose and repair the unmatched key
events |>
  anti_join(player_info, by = "player_id")

If the mismatch is merely text representation, reuse Week 4 string-standardisation tools, then rerun the diagnostic.

Still stuck?

Inspect the unmatched identifier alongside the values in the lookup table. Look for differences in case, spaces or formatting before changing either dataset.

Hint for Task 3.4 — Contrast with an inner join
events |>
  inner_join(player_info, by = "player_id")

An inner join keeps matched observations only. Judge that loss against the analytical question.

Hint for Task 3.5 — Plan the full running-case joins
analysis_data <- tracking |>
  left_join(
    players |> select(player_id, player_name),
    by = "player_id"
  ) |>
  left_join(
    matches |> select(match_id, result),
    by = "match_id"
  )

Selecting only needed lookup fields keeps the join logic visible.

Still stuck?

Build one join at a time. After the player join, verify row count and missing player_name; only then add the match join and repeat the verification.

Hint for Task 3.6 — Verify the joined analytical table
nrow(tracking)
nrow(analysis_data)
sum(is.na(analysis_data$player_name))
sum(is.na(analysis_data$result))

Then ask again what one row represents.

Hint for Task 3.7 — Use the relationship to answer a real question

Choose a question that genuinely combines context from a lookup table with performance observations—for example, one requiring player name or match result alongside tracking measures.

PHASE 4 — CHECKPOINT

Hint for Task 4.1 — Checkpoint the join workflow

A join can silently drop rows, multiply rows or change the observational unit. Verification should test the specific outcome you predicted.

PHASE 5 — TRANSFER

Hint for Task 5.1 — Identify the transfer key
testing |>
  left_join(
    squad,
    by = c("athlete_code" = "athlete_id")
  )

The names differ, but the variables can still represent the same identifier.

Hint for Task 5.2 — Predict what must be preserved

If testing observations define the analytical grain, testing should be on the left of a preserving join.

Hint for Task 5.3 — Join using the required preservation logic

Use a left join from testing to squad context.

Still stuck?

Write the key mapping explicitly as by = c("athlete_code" = "athlete_id"). Then compare the joined row count with the original testing row count.

Hint for Task 5.4 — Diagnose unmatched records

Use anti_join() in the direction that asks “which testing observations found no squad match?”

Still stuck?

Keep testing on the left and use the same key mapping as the join. The output should contain only testing rows whose identifier did not match the squad table.

Hint for Task 5.5 — Verify the transfer join

Compare expected and observed row counts and inspect missing added fields. A plausible result is one consistent with the grain and known matching structure.

PHASE 6 — EXTENSION

Hint for Task 6.1 — Predict row multiplication from role history

If an athlete has two seasonal role records, a join on athlete alone can create two rows from one testing observation. A defensible key may need both athlete identity and season, or a deliberately selected “current role” table.

PHASE 7 — DEBRIEF

Hint for Task 7.1 — Explain what a join assumes

Every join asserts that particular fields identify corresponding entities and that a particular set of observations should be preserved. Those are analytical assumptions, not merely syntax.

If your R code isn’t working
  1. Check the Week 5 project and setup objects exist.
  2. Use names(), glimpse() and nrow() before joining.
  3. Confirm the key columns contain the identities you think they contain.
  4. Run one join at a time.
  5. Use anti_join() to diagnose unmatched keys.
  6. After every join, check row count, missing joined fields and grain.
