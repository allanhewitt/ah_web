PHASE 2: CORE: THE MATCHES TABLE

Same patterns as the demonstration, different table and columns.

Hint for Task 2.1: Grain of matches

Complete the sentence “One row is one ...” using what you saw in glimpse(). Then ask what it would mean if the same ID appeared twice in a table whose rows are supposed to be unique.

Hint for Task 2.2: Dimensions and names
nrow(table)
ncol(table)
names(table)

These are expectation checks, not sophisticated analyses.

Hint for Task 2.3: Representations that matter
class(table$column)

Repeat for each column. Ask whether the class would change what later code means, not whether another class is merely possible.

Hint for Task 2.4: Convert and verify the match dates
table$column <- as.Date(
  table$column,
  format = "%d/%m/%Y"
)

class(table$column)
sum(is.na(table$column))
head(table$column)
min(table$column)
max(table$column)

Check the date format in the original column first, so that the format matches what is actually stored. To keep the original, assign to a new name on the left of <-, and then check the new column. A valid Date class and zero NAs are not enough: inspect the actual values and the range.

Hint for Task 2.5: Missingness and plausibility in matches
sum(is.na(table$column))
min(table$column)
max(table$column)

Missingness and plausibility are different checks. Ask whether the smallest and largest values are believable for what the column measures.

PHASE 3: CORE: THE TRACKING TABLE

Same patterns, larger table.

Hint for Task 3.1: Grain of tracking

Look at which columns identify a row. If both a player and a match are needed to identify it, what is one row?

Hint for Task 3.2: Dimensions, names and expectations
nrow(table_a)
nrow(table_b)
nrow(table_a) / nrow(table_b)

Interpret the result as “rows of tracking per row of matches”. What does that say about how many players are tracked in each match?

Hint for Task 3.3: Representations that matter
class(table$column)

Identifiers identify, quantities measure. Ask whether the class matches the role.

Hint for Task 3.4: Missingness in tracking
sum(is.na(table$column))

Run it once for each numerical variable. Zero is a finding too.

Hint for Task 3.5: Plausibility in tracking
min(table$column)
max(table$column)

If a result comes back as NA, think about what min() does when a value is missing. Look up the na.rm argument with ?min, and think about what it changes and what it hides. Then judge the range: is a value possible, and is it typical?

PHASE 4: IDENTIFIERS AND TRUST

Coverage tests and the trust statement.

Hint for Task 4.1: Identifier coverage
all(table_a$id_column %in% table_b$id_column)

Read it as: is every value in the first column found in the second? Use the tracking column on the left and the reference table on the right. If it returns FALSE, identify the values that failed before deciding the data are wrong.

Hint for Task 4.2: Does the direction matter?

Swap the two sides of the same pattern. Think about what each FALSE would mean: a tracking row with no reference record, versus a reference record with no tracking rows. Are these equally worrying for a join in Week 5?

Hint for Task 4.3: Write a trust statement

A useful structure is:

  • Verified: what the checks support;
  • Uncertain: what cannot be established from these checks alone.

A passed check supports a claim about structure. It does not prove every measurement is accurate.

PHASE 5: TRANSFER

Use these prompts to avoid “cleaning” legitimate unusual values.

Hint for Task 5.1: Diagnose the athletics results before changing them
  • Start with glimpse() and head(), then compare what R shows with what the file contains.
  • DNS may be meaningful information rather than a typo.
  • A code such as 01 may be an identifier rather than a quantity. Compare the class R chose with the role of the variable.
  • Mixed date formats can obstruct analysis even when a human can read each date. After converting, count the NAs and find which values produced them.
  • Do not change an unusual value merely to make a column easier to summarise.
Hint for Task 5.2: Make only defensible changes

Ask: Do I have evidence that this value is wrong, or only evidence that it is inconvenient? If the original source is needed to decide, flag the issue rather than inventing certainty.

PHASE 6: EXTENSION

Go beyond the patterns.

Hint for Task 6.1: Check the structure you expected
table(tracking$match_id)
table(tracking$match_id, tracking$position)

table() counts how often each value occurs. The first line gives rows per match. The second cross-tabulates match by position. Scan the counts for anything a real match would not produce.

Hint for Task 6.2: Produce a trust audit

Keep the audit short. Strong answers clearly separate checks you actually performed from claims that would require metadata, documentation or the original provider.
