PHASE 1 — RETRIEVAL

Use these prompts only if the three claims are difficult to unpack.

Hint for Task 1.1 — Test three claims

Separate representation from analytical meaning, remember that successful import does not validate contents, and use grain to decide whether repeated IDs are expected.

PHASE 2 — CONSEQUENCE PROBLEM

Think in terms of evidence needed before a report is defensible.

Hint for Task 2.1 — Decide what must happen first

Useful categories are structure, representation, missingness/plausibility and identifier coverage. You are not trying to prove the file is perfect; you are trying to establish what can be trusted.

PHASE 3 — CORE PRACTICAL

Reveal only the syntax or reasoning your group needs.

Hint for Task 3.1 — Establish the grain of each table
glimpse(players)
head(players)
glimpse(matches)
glimpse(tracking)

The grain is what one row represents. State it in words before treating repeated IDs as a problem.

Hint for Task 3.2 — Check that the objects are what you expected
nrow(players)
ncol(players)
names(players)

Repeat for the other tables. These are expectation checks, not sophisticated analyses.

Hint for Task 3.3 — Check representations that matter
class(players$player_id)
class(players$squad_number)
class(players$contract_end)

Inspect variables whose representation could change what later code means. You do not need to convert a variable merely because another class is possible.

Hint for Task 3.4 — Convert and verify the contract dates
players$contract_end <- as.Date(
  players$contract_end,
  format = "%d/%m/%Y"
)

class(players$contract_end)
sum(is.na(players$contract_end))
head(players$contract_end)
min(players$contract_end)
max(players$contract_end)

A valid Date class and zero unexpected NAs are not enough on their own. Inspect actual values and plausible bounds.

Hint for Task 3.5 — Check missingness and plausibility
sum(is.na(tracking$match_rating))
min(tracking$distance_km, na.rm = TRUE)
max(tracking$distance_km, na.rm = TRUE)

Missingness and plausibility are different checks. A recorded value can still deserve investigation.

Hint for Task 3.6 — Check identifier coverage
all(tracking$player_id %in% players$player_id)
all(tracking$match_id %in% matches$match_id)

If a check returns FALSE, identify the values that failed before deciding that the data are wrong.

Hint for Task 3.7 — Write a trust statement

A useful structure is:

  • Verified: what the checks support;
  • Uncertain: what cannot be established from these checks alone.

PHASE 4 — CHECKPOINT

Use the sequence to check the logic of your work.

Hint for Task 4.1 — Checkpoint the trust workflow

The point of the workflow is not to eliminate all uncertainty. It is to stop a successful import being mistaken for evidence that the data are analytically trustworthy.

PHASE 5 — TRANSFER

Use these prompts to avoid “cleaning” legitimate unusual values.

Hint for Task 5.1 — Diagnose the athletics results before changing them
  • DNS may be meaningful information rather than a typo.
  • A code such as 01 may be an identifier rather than a quantity.
  • Mixed date formats can obstruct analysis even when a human can read each date.
  • Do not change an unusual value merely to make a column easier to summarise.
Hint for Task 5.2 — Make only defensible changes

Ask: Do I have evidence that this value is wrong, or only evidence that it is inconvenient? If the original source is needed to decide, flag the issue rather than inventing certainty.

PHASE 6 — EXTENSION

Distinguish evidence from the file from evidence requiring provenance.

Hint for Task 6.1 — Produce a trust audit

Keep the audit short. Strong answers clearly separate checks you actually performed from claims that would require metadata, documentation or the original provider.

PHASE 7 — DEBRIEF

Return to professional responsibility rather than syntax.

Hint for Task 7.1 — Explain why inspection is professional practice

Think about what happens when a report, selection decision or intervention is based on a file whose structure or values were never checked.
