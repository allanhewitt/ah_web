WHY THIS MATTERS

Central question: What if the evidence we need is spread across different tables?

A join is part of the analysis. It can run without an error and still lose observations, duplicate them or change what one row represents, so every join needs an expectation before it and a check after it: QUESTION → TABLES → GRAIN → KEY → EXPECTATION → JOIN → VERIFY → ANALYSE.

How to work this week

In the demonstration you joined training sessions to a squad register, found two sessions that did not match, repaired one and checked the result. You then saw a join multiply rows when a third table had several rows for each player, and fixed it. Here you apply the same moves to different tables, and you judge somebody else’s join.

This week also revisits Weeks 1 to 4. Phase 1 uses the tracking table and the checks and verbs you already know, and separates numbers that measure from numbers that label, because every join is verified with the same checks and a key is only ever matched, never averaged.

Work through this page in order as a pair, in your own script (week05_session.R has a heading for each task). Keep brief comments as you go, so that your script records both what you ran and what you concluded. Most tasks start from a block in week05_demo.R.

Predict before you run. Write the number of rows you expect before every join and compare it with the result. Keep each imported table exactly as imported, and put joined results in new objects.

If your pair gets stuck, open the Week 5 Hint Sheet and use the hint for the relevant task. Use as little support as you need, then return to the task. Phases 1 to 4 are the main work of the session. Phase 5 asks you to transfer the process to different tables, including one in which a join multiplies rows, and Phase 6 is for pairs who want to go further.

Use one RStudio project for the pair and swap the person typing at the start of each phase. Both of you should be able to explain your decisions.

PHASE 1: CORE: REVISIT WEEKS 1 TO 4

Import and check tables before you join anything.

Task 1.1: Restart and import

Use Session > Restart R so that nothing from the demonstration is left in memory. Check that week_five.Rproj is the open project. Start a new script, save it, and load the tidyverse. Keep week05_demo.R open in another tab: most tasks start from a block of it.

As a pair: Import three files from the data folder: player_match_tracking.csv into tracking, match_results.csv into matches and players.csv into players. (The small tables and the athlete files are imported later.)

Record: A comment for each table saying what one row represents.

Task 1.2: Check tracking from memory

As a pair: Without looking at an earlier script, write the code that gives you: a first look at tracking; its number of rows and columns; the number of missing values in match_rating; the smallest and largest value of minutes_played and distance_km; the number of exact duplicate rows; and a count of the rows for each position.

Record: Each result as a comment beside the line that produced it, and one sentence on anything that would need attention before analysis.

Task 1.3: Choose the measure

As a pair: Among appearances of at least 60 minutes, store the filtered table in tracking_60. For each position, find the number of appearances, the number of those that have a rating, and the mean match_rating. Order the table from the highest mean to the lowest.

Record: The table as comments, what one row of it now represents, and one sentence on what the number of rated appearances tells you about how far to trust each mean.

Task 1.4: Numbers that measure and numbers that label

As a pair: In players, squad_number is stored as a number, but it labels a player. Check its class and calculate its mean. Then make a copy of players called players_checked in which squad_number is a factor, using as.factor(), check the class again and try the mean again. Say which of age, height_cm, squad_number and player_id it makes sense to average, and why.

Record: The two classes, the two means (including what R printed the second time), and one sentence that separates measurements from labels.

PHASE 2: CORE: CONNECT A SMALL PAIR

Two small tables, one key and one record that will not match.

Task 2.1: Predict before you join

As a pair: Import week05_task_events.csv into events and week05_task_player_info.csv into player_info, with trim_ws = FALSE. State what one row represents in each table and identify the key. Check whether the key is unique in each table. Then predict how many rows a left join with events on the left will give, and how many of them will have a missing player_name.

Record: The grain of each table, the key, the uniqueness result and your predictions, written as comments before you join.

Task 2.2: Join and diagnose

As a pair: Add player_info to events with a left join, keeping every event. Compare the number of rows and the number of missing names with your predictions. Then use anti_join() in both directions to find the keys that do not match, and look at them closely.

Record: Expected and observed counts, the unmatched ID in each direction, and what is different about the two keys.

Task 2.3: Decide, repair and verify

As a pair: Decide how to treat the unmatched event: repair the key, leave it, or investigate first, and give a reason. Implement your decision in a new table called events_fixed, leaving events unchanged. Join again and verify the result: the number of rows, the number of missing names, and both anti_join() directions.

Record: Your decision and its reason, the verification evidence, and one sentence on whether the repair was defensible.

Task 2.4: Contrast with an inner join

As a pair: Run inner_join() on the original events and player_info. Compare the number of rows with the left join and count the shot events before and after. Which event disappeared?

Record: The counts, the event that was lost, and what a count of shots per player would have reported without any message to say that an event was missing.

PHASE 3: CORE: CONNECT THE RUNNING CASE

The same moves on the three Strathclyde FC tables.

Task 3.1: Grain, keys and unmatched records

As a pair: State what one row represents in tracking, players and matches. Check that player_id is unique in players and that match_id is unique in matches. Use anti_join() in both directions between tracking and players, and between tracking and matches. Count how many distinct players and matches tracking contains.

Record: The three grains, the two uniqueness results, all four anti_join() results (including the empty ones) and what they tell you. An empty result is a result.

Task 3.2: Predict, then join everything

As a pair: Predict the number of rows and columns you will get if you add every column of players to tracking with a left join on player_id. Then do it and store the result in track_players. Look at the column names: what has happened to position? Check whether the two copies of it agree.

Record: Your prediction, the result, what you noticed in the column names, and whether the copies agree.

Task 3.3: Join only what you need

As a pair: Build tracking_joined, which adds only player_name from players and only result from matches to tracking, keeping every appearance. Verify it: the numbers of rows and columns, the missing player_name and result values, and whether any player appears twice in the same match.

Record: Expected and observed counts, a final statement of what one row represents, and one sentence on why it is better to select the lookup columns before joining.

Task 3.4: Answer a question with two tables

As a pair: Among appearances of at least 60 minutes in tracking_joined, calculate the mean match_rating for each match result, with the number of appearances and the number of rated appearances behind each mean. Then count the missing match_rating values in tracking_joined and compare them with Task 1.2.

Record: The table, one sentence on what you can and cannot conclude from it, and one sentence on what the join did to the missing ratings.

PHASE 4: AUDIT: JUDGE A COLLEAGUE’S JOIN

Somebody else joined the same two small tables. Do not assume that the handover note is accurate.

Task 4.1: What does each step actually do?

As a pair: Open colleague_join.R (read it, but do not edit it). Run the pipeline one step at a time, in your own script, and find the number of rows after each step. For each step, find out which rows it removed or changed.

Record: A table with one row per step: Step | Rows after | What was removed or changed | Was it justified?

Task 4.2: Verdict

As a pair: The handover note makes three claims: that every event was matched to a player, that no rows were lost, and that the table is ready to count shots per player. Check each claim against your own results from Phase 2. Then compare the colleague’s shots per player with the shots recorded in events.

Record: A verdict on each claim, two other problems you found, and the changes that would make the script defensible.

PHASE 5: TRANSFER

Different tables, different key names and the same judgement process.

Task 5.1: Plan the join first

As a pair: Import week05_transfer_squad.csv into squad and week05_transfer_testing.csv into testing, with trim_ws = FALSE. A performance lead wants the sprint and jump results alongside each athlete’s name and squad, without losing any recorded test result. Before writing any join code, build a plan table with the columns Question | Grain of each table | Key (and its name in each table) | Which observations must survive | Expected row count | How will I verify?

Record: The plan table, kept in your script as comments and filled in before you join.

Task 5.2: Join, diagnose and verify

As a pair: Implement your plan and store the result in testing_squad. Use anti_join() in both directions, verify the row count and the missing joined fields, and compare with what inner_join() would have returned.

Record: The verification evidence, the unmatched ID in each direction, and what an inner join would have lost.

Task 5.3: Decide and report

As a pair: Calculate the mean sprint_20m and the mean jump_cm for each squad in testing_squad, with the number of athletes. One athlete has no squad information. Decide what you will do with that row, and write the sentence that you would put in a report to the performance lead.

Record: The table, your decision with a reason, and the report sentence.

Task 5.4: When one athlete has several rows

As a pair: Import week05_transfer_roles_history.csv into roles_history: it records the role of each athlete in each season. Treat athlete_code in testing and athlete_id in roles_history as the same key. Check whether the key is unique in roles_history, and predict the number of rows you get if you add the role to testing by athlete alone. Run it and find the athlete who changed the count. Then reduce roles_history to one row per athlete, using the role for the current season (2026-27), join again and verify the result.

Record: Your prediction, the result, the cause, the corrected join with its verification, and one sentence on why choosing the season is a decision about meaning and not only about code.

PHASE 6: EXTENSION

Make the assumptions behind a join explicit.

Task 6.1: How far could the unmatched athlete change the answer?

As a pair: In Task 5.3, athlete A09 had no squad. Calculate the difference between the Senior and Development squads in the mean jump (Senior minus Development) and in the mean sprint time (Development minus Senior) in three cases: with A09 left out, with A09 placed in Development, and with A09 placed in Senior. Work on copies of testing_squad and leave the original unchanged.

Record: The six differences in a small table, and one sentence on whether the squad comparison could change once A09’s squad is known.

Task 6.2: A reusable check

As a pair: Write a function check_join(before, after, column) that returns a one-row table with the number of rows before, the number of rows after, and the number of missing values in column of the joined table. Use stopifnot() so that it stops with an error if column is not in after. Test it on a join from Phase 2, Phase 3 and Phase 5, and check that it fails sensibly when you give it a column name that does not exist.

Record: The function, its results on the three joins, and what the failed test printed.

Task 6.3: Decision log for unmatched records

As a pair: The athlete who has a test result but no squad record could be a trialist, or could be a mistake in the athlete code. The athlete in the squad with no test result could be injured, absent or not yet tested. Explain what additional information you would seek before changing anything.

Record: A short decision log for the two athletes: what you know, what you do not know, who you would ask, and what you would do in the meantime.

PHASE 7: DEBRIEF

Connect careful joining with professional accountability.

Task 7.1: What does a join assume?

As a pair: A join is not merely a technical way to add columns. What does a left join assume about identity, preservation and relationships? Give one example from today where an assumption held and one where it failed.

Record: Two or three sentences.

Task 7.2: Can somebody else check your work?

As a pair: Why should an analyst be able to show somebody who did not write the code what was expected, what was checked and what was decided? Use what you found in the colleague’s script to support your answer.

Record: One or two sentences focused on evidence and reproducibility.

Assessment One connection: describing how tables relate, using anti_join() to find unmatched keys, choosing left_join() so that the right rows survive, understanding what inner_join() would discard, and verifying the row count while keeping unmatched records visible as missing values are core. A join is also a check on whether two files agree about their keys. right_join() and pivot_wider() are extension.
