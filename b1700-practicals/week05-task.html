Connecting Data Sources

Group Task Sheet · Core → Transfer → Extension

Why this matters

Central question: What if the evidence we need is spread across different tables?

Incorrect joins can lose observations, duplicate observations or silently change the grain. Relationships between datasets are part of the analysis.

How to work this week

Work through this page in order as a small group. Use the Week 5 RStudio project and keep notes in week05_session.R. Predict what a join should do before running it, then verify afterwards.

If your group gets stuck, open the Week 5 Hints and reveal only the support you need.

PHASE 1 — RETRIEVAL

Predict the relationship before using a join function.

Task 1.1 — Recall grain and preservation

As a group, without running code: What does one row in players represent? What does one row in tracking represent? Is player_id unique in both tables? What should happen to the number of tracking rows if player information is added correctly while preserving every tracking observation?

Record: Write four short answers in the Phase 1 workspace.

PHASE 2 — CONSEQUENCE PROBLEM

A join running successfully does not prove that the relationship is correct.

Task 2.1 — Interpret an unexpected row loss

A join runs without an R error. The resulting table contains fewer rows than the table you started with.

As a group: Is that necessarily a problem? What would you need to know before deciding?

Record: Write a short response using grain, key and preservation logic.

PHASE 3 — CORE PRACTICAL

Connect data while protecting the intended grain and observations.

Task 3.1 — Predict the small join

Inspect week05_join_demo_events.csv and week05_join_demo_player_info.csv.

As a group: Identify the intended key, state the grain of the events table and predict which record will fail to match.

Record: Record the key, grain and prediction before joining.

Task 3.2 — Use a left join with an explicit expectation

As a group: Use a left join with events on the left. Before running it, state which observations should be preserved and the row count you expect. Verify the result afterwards.

Record: Keep the expected and observed row counts.

Task 3.3 — Diagnose and repair the unmatched key

As a group: Identify the unmatched record, diagnose the identifier inconsistency, repair it, and verify that the left join now behaves as expected.

Record: Record the mismatch, repair and verification evidence.

Task 3.4 — Contrast with an inner join

As a group: Compare the result with an inner join. Explain which observation would disappear and why that may or may not be appropriate for a particular analytical question.

Record: Write a preservation-based explanation, not just a definition of inner join.

Task 3.5 — Plan the full running-case joins

The project contains players, matches and tracking.

As a group: State the grain and expected row count before adding player_name and match result to tracking. Join only the lookup fields needed so duplicate context columns do not obscure the relationship.

Record: Write the expected grain and row count before joining.

Task 3.6 — Verify the joined analytical table

As a group: Verify the joined table using row count and missing joined fields. Confirm that one row still represents one player appearance in one match.

Record: Keep the verification evidence and final grain statement.

Task 3.7 — Use the relationship to answer a real question

As a group: Answer one question that genuinely requires information from more than one original table.

Record: Write the question, analysis and a short interpretation.

PHASE 4 — CHECKPOINT

Treat expectation and verification as part of every join.

Task 4.1 — Checkpoint the join workflow

QUESTION → TABLES → GRAIN → KEY → EXPECTATION → JOIN → VERIFY → ANALYSE

As a group: Explain why “the join ran” is not adequate verification.

Record: Write one sentence identifying what a join can silently change.

PHASE 5 — TRANSFER

Apply the same preservation logic when key names differ.

Task 5.1 — Identify the transfer key

Open week05_transfer_squad.csv and week05_transfer_testing.csv.

As a group: Identify the key and the different key names used in the two files.

Record: Record the key relationship.

Task 5.2 — Predict what must be preserved

A performance lead wants sprint and jump results alongside athlete name and squad while preserving every recorded testing observation.

As a group: State the grain of testing and predict the row count that should be preserved.

Record: Record the grain and expected row count.

Task 5.3 — Join using the required preservation logic

As a group: Join the files so that every testing observation is preserved while athlete context is added.

Record: Keep the joined table.

Task 5.4 — Diagnose unmatched records

As a group: Diagnose unmatched records in the relevant direction rather than assuming that missing joined fields are acceptable.

Record: Record any unmatched identifiers.

Task 5.5 — Verify the transfer join

As a group: Verify the final row count and missing joined fields, then decide whether the result is plausible.

Record: Write a short verification statement.

PHASE 6 — EXTENSION

Explore how a many-to-one assumption can fail when time enters the relationship.

Task 6.1 — Predict row multiplication from role history

Open week05_challenge_roles_history.csv. The same athlete can appear more than once because roles are recorded by season. The testing table uses athlete_code; the history table uses athlete_id. Treat these as the same athlete key.

As a group: Predict what could happen if current testing is joined to role history using athlete identity alone, without season. What happens to grain and row count? How would you redesign the data or key before joining?

Record: Write the predicted failure mode and your redesign.

PHASE 7 — DEBRIEF

Make the assumptions encoded by a join explicit.

Task 7.1 — Explain what a join assumes

As a group: A join is not merely a technical way to add columns. What assumptions about identity, preservation and relationships does it encode?

Record: Write one or two sentences capturing those assumptions.
