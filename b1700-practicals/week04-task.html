Week 4 · Task Sheet

Dealing with Messy Data

Group Task Sheet · Core → Audit → Transfer → Extension

WHY THIS MATTERS

Central question: What is genuinely wrong, and what change is defensible?

Cleaning changes evidence. Every deletion, replacement and recoding decision can change the result, so each one needs a reason and a check: DIAGNOSE → DECIDE → CLEAN → VERIFY.

How to work this week

In the demonstration you diagnosed, flagged, cleaned and verified a table of training sessions. Here you apply the same moves to a table of player appearances that has more problems, and you then judge somebody else’s attempt to clean it.

This week also revisits Weeks 1 to 3. Phases 1 and 2 use trusted tables and the checks and verbs you already know. Later phases ask you to use them again, because every cleaning decision is verified with the same checks, and every comparison uses the same verbs.

Work through this page in order as a small group, in your own script (week04_session.R has a heading for each task). Keep brief comments as you go, so that your script records both what you ran and what you concluded. Most tasks start from a block in week04_demo.R.

Diagnose before you change anything. Keep dirty exactly as imported and put cleaned results in a new object. A flag is a prompt to investigate, not a verdict.

If your group gets stuck, open the Week 4 Hint Sheet and use the hint for the relevant task. Use as little support as you need, then return to the task. Phases 1 to 6 are the main work of the session. Phase 7 asks you to transfer the process to a new table, and Phase 8 is for groups who want to go further.

Use one active RStudio project per group and rotate the person operating RStudio. Everyone should be able to explain the group’s decisions.

PHASE 1: CORE: REVISIT WEEKS 1 AND 2

Start clean, import, and check a table before you do anything to it.

Task 1.1: Restart and import

Use Session > Restart R so that nothing from the demonstration is left in memory. Check that week_four.Rproj is the open project. Start a new script, save it, and load the tidyverse. Keep week04_demo.R open in another tab: most tasks start from a block of it.

As a group: Import three files from the data folder: player_match_tracking.csv into tracking, match_results.csv into matches and players.csv into players. (The messy extract and the other files are imported later.)

Record: A comment for each table saying what one row represents.

Task 1.2: Check tracking from memory

As a group: Without looking at an earlier script, write the code that gives you: a first look at tracking; its number of rows and columns; the class of venue, minutes_played and distance_km; the number of missing values in match_rating; the smallest and largest value of minutes_played and distance_km; and a count of the rows for each position.

Record: Each result as a comment beside the line that produced it, and one sentence on anything that would need attention before analysis.

Task 1.3: Spot representation problems

As a group: Check the class of date in matches, and of contract_end and is_captain in players. Decide which of these would obstruct a later filter or comparison, and which are fine as they are.

Record: Each variable, its class, and one sentence on whether you would convert it. You will convert one of them in Task 2.3.

PHASE 2: CORE: REVISIT WEEK 3

The same verbs as Week 3, on a trusted table, before we turn to a messy one.

Task 2.1: Filter and derive

As a group: Among appearances of at least 60 minutes, create a new variable holding distance covered per 90 minutes. Store the result in a new object called tracking_60. Verify it: how many rows remain, the smallest value of minutes_played, and the smallest and largest value of the new variable.

Record: The three checks, and a sentence on whether the range is plausible for football.

Task 2.2: Group, summarise and arrange

As a group: Compare the positions on mean distance per 90 and the number of appearances in each, ordered from the highest mean to the lowest. Use your football knowledge to judge whether the ordering is what you would expect.

Record: The table as comments, what one row of it now represents, and one unexpected feature and your explanation of it.

Task 2.3: Convert and verify the match dates

As a group: The dates in matches are stored as text in day/month/year layout. Convert them into R dates in a new column called match_date, so the original is kept. Verify the result: its class, whether any values failed to convert, and the earliest and latest date.

Record: Your verification evidence, not just that the conversion ran.

PHASE 3: CORE: DIAGNOSE THE MESSY EXTRACT

Look before you touch. Nothing in this phase changes the data.

Task 3.1: Missing and implausible values

A recorded value is not proof of a valid value. Remember that a missing value and an implausible value are different problems.

As a group: Import week04_dirty_tracking_extract.csv into dirty, keeping trim_ws = FALSE so that stray spaces stay visible. This extract has the same columns as tracking, but it has been damaged. Count the missing values in distance_km and match_rating, find the range of distance_km and minutes_played, and list every row whose distance_km is not a believable distance for one appearance.

Record: For each odd value: the row, whether you think it is impossible, unusual but plausible, or unknown, and the evidence for that judgement.

Task 3.2: Duplicates relative to grain

As a group: State what one row of dirty should represent. Count the exact duplicated rows and find them. Then check whether any player appears twice in the same match with different values in the other columns. Explain why a repeated player_id is not a duplicate in itself.

Record: The grain, the duplicate count, which rows are involved, and your justification for treating them as duplicates (or not).

Task 3.3: Inconsistent labels

As a group: Count how many distinct values position has, and how many positions the squad actually uses. Decide which labels are the same position written differently. Work out what trimming spaces and standardising case would fix, and what they would leave behind.

Record: The distinct labels before cleaning, and a mapping from every label to the position it should become.

Task 3.4: Flag candidates

A flag marks a row for review. It does not change the data and it does not tell you what to do.

As a group: Take the flagging block from your demonstration script and apply it to distance_km. List the rows each rule flags. Compare the two rules: which values does each catch, which does it miss, and why?

Record: The flagged rows, and one sentence explaining the difference between the rules. Nothing is changed in this task.

Task 3.5: Look at it

As a group: Draw a histogram and a horizontal boxplot of distance_km in dirty, using the two lines from your demonstration script. Find the rows you flagged in Task 3.4 on the picture.

Record: One sentence on what the picture shows that the table did not, and one on why the box is so hard to see. Nothing is changed in this task.

PHASE 4: CORE: DECIDE, CLEAN, VERIFY

Make each change traceable to evidence, then show that it did what you intended.

Task 4.1: Decision table

As a group: Before writing cleaning code, build a decision table with the columns Issue | Evidence | Decision | Rule or reason | How will we verify? Include every problem you found in Phase 3. Choose a decision for each from: change, leave, or investigate first.

Record: The table, kept in your script as comments. Be ready to explain your rule for impossible distances.

Task 4.2: Clean

As a group: Write one pipeline that starts from dirty and stores the result in dirty_clean. It should implement your decisions: standardise the position labels, represent clearly impossible distances as missing, and remove duplicates. Do not invent replacement values. Leave dirty itself unchanged.

Record: The pipeline, with a comment against each line saying which row of your decision table it implements.

Task 4.3: Verify, then flag again

As a group: Re-run the diagnostics from Phase 3 on dirty_clean: the number of rows, the missing values in each column, the range of distance_km, the duplicate count and the distinct position labels. Compare each with your starting numbers. Draw the boxplot of distance_km again. Then apply the flagging block again. Decide what to do with anything new that is flagged.

Record: A before and after table of the checks, what changed and what did not, one sentence on how the boxplot changed, and a decision for any new flag.

Task 4.4: Does cleaning change the answer?

As a group: Build dirty_labels: your Task 4.2 pipeline without the line that converts impossible distances. Calculate mean distance_km by position for both dirty_labels and dirty_clean, with the number of rows behind each mean.

Record: Both tables, the position whose conclusion changes most, and one sentence on what an analyst who skipped the cleaning would have reported.

Task 4.5: What would dropping cost?

As a group: In dirty_clean, count the rows that na.omit() would remove. Compare that with the rows that have a missing distance_km. Find the rows that would be lost only because of a missing match_rating. If your question is about distance, what would dropping those rows do?

Record: The three counts, and one sentence on why dropping every row with a missing value is rarely the best default.

Task 4.6: Impute, mark and compare

As a group: The question is: what is the mean distance for each position? Create dirty_imputed, in which each missing distance_km is replaced with the median distance of that player’s position, and add a column distance_imputed that is TRUE for the rows you filled in. Leave match_rating as it is. Then calculate the mean distance by position, with the number of rows, for three versions: leaving the missing values (with na.rm = TRUE), replacing them with the overall median, and replacing them with the position median.

Record: The three versions side by side, how many values were imputed in each position, which version you would report, and why match_rating should not be treated in the same way.

PHASE 5: CORE: RESHAPE

A different kind of problem: the shape of the table.

Task 5.1: Wide to long

As a group: Import week04_training_load_wide.csv into training_wide. State what one row represents. Reshape the table so that the week becomes a variable and the training load becomes a value, and store it in training_long. Check the number of rows before and after.

Record: The grain before and after reshaping, and both row counts.

Task 5.2: Use the long table

As a group: Calculate the mean load for each week. Then apply the flagging block to the load values. Decide what, if anything, the flags tell you.

Record: The weekly means, the flag results, and one sentence on what it means when a flag finds nothing.

PHASE 6: AUDIT: JUDGE A COLLEAGUE’S SCRIPT

Somebody else cleaned the same extract. Do not assume that the handover note is accurate.

Task 6.1: What does each step actually do?

As a group: Open colleague_cleaning.R (read it, but do not edit it). Run the pipeline one step at a time, in your own script, and find the number of rows after each step. For each step, find out which rows it removed or changed.

Record: A table with one row per step: Step | Rows after | What was removed or changed | Was it justified?

Task 6.2: Verdict

As a group: The handover note makes three claims: that the rows with problems were removed, that the positions are consistent, and that the impossible distances are gone. Check each claim against the evidence. Then compare the colleague’s mean distance by position with your own from Task 4.4.

Record: A verdict on each claim, two other problems you found, and the three changes that would make the script defensible.

PHASE 7: TRANSFER

A new sport, a small table and the same judgement process.

Task 7.1: Decision table first

As a group: Import week04_transfer_rugby.csv into rugby, again with trim_ws = FALSE. Before writing any cleaning code, build a decision table: Issue | Why it matters | Change, leave or investigate? | How would I verify? Pay particular attention to the position labels, repeated player IDs, missing values, minutes = 95 and wellness = 999. Do not assume that every unusual value should be changed.

Record: The decision table.

Task 7.2: Clean, flag and compare

As a group: Implement the decisions you are confident about. Apply the flagging block to minutes and to wellness. Does either rule flag the 95-minute value? Does either flag the 999? Then compare mean wellness by position before and after cleaning. Finally, work out what proportion of wellness is now missing, and decide whether you would be willing to impute it.

Record: The verification evidence, what each flag did and did not catch, the before and after means, and your decision on imputing with a reason.

PHASE 8: EXTENSION

Make uncertainty explicit instead of cleaning it away.

Task 8.1: How much could the missing values matter?

As a group: Instead of guessing one value for each missing distance, find the range of answers that the missing values allow. Replace every missing distance_km in dirty_clean first with the smallest valid distance and then with the largest, and calculate the mean distance by position each time. Compare the range for each position with the answer you reported in Task 4.6.

Record: A table with the lowest possible mean, the highest possible mean and your Task 4.6 mean for each position, and a sentence on whether the ranking of the positions could change.

Task 8.2: A reusable flagging function

As a group: Turn your flagging block into a function called flag_outliers(data, column) that returns the table with iqr_flag, z and z_flag added. Use stopifnot() so that it stops with an error if the column does not exist or is not numeric. Test it on distance_km in dirty and on duration_min in the demonstration table, and check that it fails sensibly when you give it a text column.

Record: The function, its results on both tables, and what the failed test printed.

Task 8.3: Decision log for ambiguous values

As a group: Assume the 95-minute value could represent extra time, and the value 999 could be a missing-value code or a data-entry error. Explain what additional information you would seek before modifying either record.

Record: A short decision log for the two values: what you know, what you do not know, who you would ask, and what you would do in the meantime.

PHASE 9: DEBRIEF

Connect careful cleaning with professional accountability.

Task 9.1: Flag or change?

As a group: What is the difference between flagging a value and changing it? Give one example from today where a flag led to the right decision and one where a flag was incomplete, misleading or silent.

Record: Two examples with one sentence each.

Task 9.2: Why must cleaning be auditable?

As a group: Why should an analyst be able to explain and verify a cleaning decision to somebody who did not write the code? Use what you found in the colleague’s script to support your answer.

Record: One or two sentences focused on evidence and reproducibility.

Assessment One connection: missingness and plausibility (including the choice to leave, drop or replace a missing value), duplicates relative to grain, string standardisation and recoding, pivot_longer() and verification after cleaning are core. Flagging unusual values is a way of applying plausibility checks, and interpreting a flag is a judgement, not a function. pivot_wider() is extension.
